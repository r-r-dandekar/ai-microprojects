# PRD: ABC Ltd. Progress Tracker

**Based on:** 001-intent.md, 003-decisions.md
**Status:** Ready for implementation

---

## Problem Statement

ABC Ltd. has multiple departments, each with a manager responsible for ensuring tasks are completed on time. Currently there is no centralised system for tracking who is working on what, what the status of each task is, or whether deadlines are being met. Managers have no visibility across the organisation, and employees have no structured way to report their progress.

---

## Solution

A web-based progress tracker internal tool for ABC Ltd. Managers can create tasks, assign them to employees in their department, and monitor progress across the whole organisation. Employees can view all tasks in their department and update the status of their own assigned tasks. Both roles access the app via a username/password login. The app is built with React (Vite) + Bootstrap and uses Supabase as the database backend.

## User Stories

### Authentication & Onboarding

1. As an employee, I want to sign up with my email, username, and password, so that I can create an account to access the system.
2. As an employee, I want to select my department during sign-up, so that I am immediately associated with the correct team.
3. As a manager, I want to sign up and select "Manager" as my role, so that I gain the appropriate permissions upon login.
4. As a user, I want to log in using either my email or username plus my password, so that I have flexibility in how I authenticate.
5. As a user, I want my session to persist across browser closes, so that I do not have to log in every time I open the app.
6. As a user, I want to log out, so that my session is cleared from this device.
7. As a user, I want to see a clear error message if my login credentials are wrong, so that I know to try again.
8. As a user, I want my password to be stored securely, so that my credentials are not exposed in the database.

### Department Management

9. As a manager, I want to create a new department, so that new teams can be added to the organisation without needing database access.
10. As a user signing up, I want to see a list of existing departments to choose from, so that I can join the correct team.
11. As a manager, I want to see a list of all departments in the organisation, so that I can understand the org structure.

### Task Management — Manager

12. As a manager, I want to create a task with a title and optional description, so that I can define work to be done.
13. As a manager, I want to assign a task to a specific employee in my department, so that there is clear ownership.
14. As a manager, I want to set a priority (Low, Medium, High) on a task, so that employees know what to focus on.
15. As a manager, I want to optionally set a due date on a task, so that time-sensitive work has a clear deadline.
16. As a manager, I want to edit a task I created (title, description, priority, due date, assignee), so that I can correct mistakes or update details.
17. As a manager, I want to delete a task I created in my department, so that I can remove work that is no longer relevant.
18. As a manager, I want to see all tasks across all departments, so that I have full organisational visibility.
19. As a manager, I want to filter tasks by department, status, or priority, so that I can quickly find relevant information.

### Task Management — Employee

20. As an employee, I want to see all tasks assigned within my department, so that I understand the team's workload.
21. As an employee, I want to update the status of a task assigned to me, so that my manager knows my progress.
22. As an employee, I want to choose from five statuses — Pending, In Progress, Under Review, Completed, Blocked — so that my status is precise and meaningful.
23. As an employee, I want to add a short description when updating a task's status (e.g. the outcome if completed, the reason if blocked), so that my manager has context without needing to follow up.
24. As an employee, I want to see the priority and due date of my tasks, so that I can manage my time effectively.
25. As an employee, I want to filter or sort tasks by status or priority, so that I can focus on what is most urgent.

### Dashboard

26. As a user, I want to land on a dashboard after login, so that I immediately see a summary of the current state of work.
27. As an employee, I want the dashboard to show task counts by status for my department, so that I can see the team's overall progress at a glance.
28. As a manager, I want the dashboard to show task counts by status across all departments, so that I have an organisation-wide view.
29. As a manager, I want the dashboard to highlight overdue tasks, so that I can take action quickly.
30. As a user, I want to click a status card on the dashboard to navigate to the filtered task list, so that I can drill into the detail easily.

## Implementation Decisions

### Architecture

- **Frontend:** React 18 with Vite, TypeScript, Bootstrap 5 for all styling.
- **Backend/Database:** Supabase (PostgreSQL). Used purely as a database — Supabase Auth is NOT used.
- **Auth:** Fully custom. User credentials stored in a `users` table in Supabase. Passwords hashed with bcrypt on the client before being stored. Session stored in localStorage as a serialised user object (no password hash included).
- **Deployment:** Netlify or Vercel (free tier static hosting). Supabase URL and anon key stored as environment variables.

### Database Schema

**`departments` table**
- `id` (uuid, PK, default gen_random_uuid())
- `name` (text, unique, not null)
- `created_at` (timestamptz, default now())

**`users` table** (custom — does not use Supabase Auth)
- `id` (uuid, PK, default gen_random_uuid())
- `email` (text, unique, not null)
- `username` (text, unique, not null)
- `password_hash` (text, not null)
- `role` (text, check: `manager` | `employee`, not null)
- `department_id` (uuid, FK → departments.id, not null)
- `created_at` (timestamptz, default now())

**`tasks` table**
- `id` (uuid, PK, default gen_random_uuid())
- `title` (text, not null)
- `description` (text, nullable)
- `status` (text, check: `pending` | `in_progress` | `under_review` | `completed` | `blocked`, default `pending`)
- `status_note` (text, nullable) — short description provided alongside a status update
- `priority` (text, check: `low` | `medium` | `high`, default `medium`)
- `due_date` (date, nullable)
- `assignee_id` (uuid, FK → users.id, nullable)
- `created_by` (uuid, FK → users.id, not null)
- `department_id` (uuid, FK → departments.id, not null)
- `created_at` (timestamptz, default now())

### Modules

**Auth Module**
- `signup(email, username, password, role, departmentId)` — validates uniqueness of email and username, hashes password with bcrypt, inserts into `users`, writes session (without password hash) to localStorage.
- `login(identifier, password)` — identifier can be email or username; queries Supabase for matching user, compares bcrypt hash, writes session to localStorage on success.
- `logout()` — removes session key from localStorage.
- `getSession()` — reads and returns current user object from localStorage, or null.

**AuthContext**
- Provides `currentUser`, `role`, `departmentId`, `isManager`, `isEmployee`, `login`, `logout` to the component tree via React context.
- On mount, reads session from localStorage via `getSession()`.
- All routes except `/login` and `/signup` are protected; unauthenticated users are redirected to `/login`.

**Department Module**
- `listDepartments()` — returns all departments ordered by name.
- `createDepartment(name)` — inserts new department; rejects duplicates.

**Task Module**
- `listTasks(currentUser, filters?)` — managers receive all tasks across all departments; employees receive only tasks in their own department. Supports filters: status, priority, departmentId.
- `createTask(data, currentUser)` — manager only; inserts task with `created_by` and `department_id` taken from the current manager's session.
- `updateTask(id, data, currentUser)` — managers can update any field on tasks they created; employees can only update `status` and `status_note` on tasks where `assignee_id` matches their own id.
- `deleteTask(id, currentUser)` — manager only; deletes task only if `created_by` matches current user.

**Dashboard Page**
- Fetches task counts grouped by status.
- Employees: counts scoped to their department.
- Managers: counts across all departments, plus a per-department breakdown table.
- Overdue section: tasks where `due_date < today` and status is not `completed`.
- Each status card is a link to the Task List page pre-filtered by that status.

**Task List Page**
- Tasks displayed in a Bootstrap table.
- Filter controls: Status dropdown, Priority dropdown, title text search. Managers also see a Department dropdown.
- Sort by due date, priority, or created date.
- Employees: see all department tasks; "Update Status" button only on their own assigned tasks.
- Managers: see all tasks; Edit and Delete buttons only on their own department's tasks they created.
- "New Task" button visible to managers only.

**Layout / Navigation**
- Fixed top navbar: app name on the left, username and logout on the right.
- Left sidebar with links: Dashboard, Tasks, Departments (managers only).
- Active route highlighted in sidebar.

### Permissions Summary

| Action | Manager (own dept) | Manager (other dept) | Employee (own dept) |
|---|---|---|---|
| Create task | Yes | No | No |
| Edit task | Yes | No | No |
| Delete task | Yes | No | No |
| Update task status | Yes | No | Own assigned tasks only |
| View tasks | Yes | Yes (read-only) | Yes (read-only) |
| Create department | Yes | Yes | No |
| View departments | Yes | Yes | Yes |

## UI Aspects

### General

- Bootstrap 5 used for all layout, components, and utilities.
- Colour palette: professional and neutral. Bootstrap primary (blue) for primary actions; success (green) for completed status; warning (yellow) for in-progress and pending; danger (red) for blocked and overdue; info (teal) for under review.
- Client-side routing via React Router — no full page reloads.
- Responsive — must work on desktop and tablet. Mobile not a priority but must not break.
- No custom CSS framework alongside Bootstrap. Minimal custom CSS only where Bootstrap cannot achieve the result.

### Login / Signup Pages

- Centred card on a light grey (`bg-light`) full-height background.
- Login card: "Email or Username" text input, "Password" password input, "Log In" primary button. Link below: "Don't have an account? Sign up."
- Signup card: Email input, Username input, Password input, Role dropdown (Employee / Manager), Department dropdown (populated from DB). "Sign Up" primary button. Link: "Already have an account? Log in."
- Inline validation error messages displayed beneath each field that fails validation.
- A general error alert (Bootstrap `alert-danger`) displayed above the form for failed login.
- No forgot-password flow.

### Layout (post-login)

- Fixed top navbar (`navbar-dark bg-primary`): app name "ABC Progress Tracker" on the left as a brand; right side shows `Hello, <username>` and a "Logout" button.
- Left sidebar (~220px wide, full height, `bg-light border-end`): navigation links — Dashboard, Tasks, Departments (managers only). Active link highlighted with `active` class.
- Main content area fills remaining width with padding.
- On tablet, sidebar collapses to icon-only or toggled via a hamburger button.

### Dashboard Page

- Page heading: "Dashboard". Subheading: "Welcome back, <username>."
- Row of Bootstrap cards (one per status): Pending, In Progress, Under Review, Completed, Blocked. Each card shows the status name, a large count number, and a coloured top border. Entire card is clickable and navigates to `/tasks?status=<status>`.
- Overdue Tasks section below the cards: Bootstrap table with columns — Task Title, Department (managers only), Assignee, Due Date. Rows only appear if `due_date < today` and status is not `completed`. If no overdue tasks, show a muted "No overdue tasks." message.
- Managers see an additional Department Breakdown section: a Bootstrap table where rows = departments, columns = statuses (Pending / In Progress / Under Review / Completed / Blocked), cells = counts.

### Task List Page

- Page heading: "Tasks". "New Task" button (primary, top-right) visible to managers only.
- Filter bar: Status dropdown (All / Pending / In Progress / Under Review / Completed / Blocked), Priority dropdown (All / Low / Medium / High), title text search input. Managers additionally see a Department dropdown (All / <dept names>). All filters apply in combination.
- Tasks displayed in a Bootstrap `table table-hover table-bordered`.
- Columns: Title, Department (managers only), Assignee, Status, Priority, Due Date, Actions.
- Status column: Bootstrap badge, colour-coded — pending = `bg-secondary`, in_progress = `bg-warning text-dark`, under_review = `bg-info text-dark`, completed = `bg-success`, blocked = `bg-danger`.
- Priority column: Bootstrap badge — low = `bg-secondary`, medium = `bg-warning text-dark`, high = `bg-danger`.
- Due Date column: if past due and status is not completed, render the date in red text with a small "Overdue" badge.
- Actions column:
  - Employee: "Update Status" button (`btn-sm btn-outline-primary`) only on rows where `assignee_id` equals current user's id.
  - Manager: "Edit" (`btn-sm btn-outline-secondary`) and "Delete" (`btn-sm btn-outline-danger`) only on tasks where `created_by` equals current user's id. No action buttons on other departments' tasks.
- Empty state: centred muted text "No tasks found." If manager, also show "Create the first task" link.

### Task Modals

- **Create / Edit Task Modal** (managers):
  - Title: "Create Task" or "Edit Task".
  - Fields: Title (text input, required), Description (textarea, optional, max 500 chars), Assignee (dropdown of employees in manager's own department, optional), Priority (select: Low / Medium / High, default Medium), Due Date (date input, optional).
  - Footer: "Save" primary button, "Cancel" secondary button.
  - Validation: Title is required; show inline error if empty on submit.

- **Update Status Modal** (employees):
  - Title: "Update Task Status".
  - Fields: Status (select: Pending / In Progress / Under Review / Completed / Blocked), Status Note (textarea, labelled "Add a note — e.g. reason for block, or outcome if completed", optional).
  - Footer: "Update" primary button, "Cancel" secondary button.

- Both modals use Bootstrap's modal component. Backdrop click dismisses the modal.

### Departments Page (managers only)

- Page heading: "Departments". "Create Department" button (primary, top-right).
- Bootstrap table: columns — Department Name, Created Date, Actions (none for now).
- "Create Department" opens a small modal with a single "Department Name" text input, and Save / Cancel buttons.
- If a duplicate name is submitted, show an inline error: "A department with this name already exists."

### Error & Empty States

- Loading: Bootstrap spinner (`spinner-border text-primary`) centred in the content area while data fetches.
- Network/unexpected errors: Bootstrap `alert alert-danger` banner at top of content area with a generic message and a retry option.
- Failed login: `alert alert-danger` above the login form.
- Empty task list: muted centred text "No tasks found."
- Empty department list: muted centred text "No departments yet."

### Avoided Pitfalls

- Employees must never see tasks outside their own department — enforced in the Task Module's `listTasks`, not just in the UI.
- Edit/Delete/New Task controls must never render for employees — conditional rendering based on `isManager` from AuthContext.
- A manager must not be able to edit or delete tasks from another department — enforced in `updateTask` and `deleteTask` by checking `created_by`.
- The password hash must never be included in the localStorage session object or returned to the UI.
- On logout, localStorage must be cleared before navigating to `/login` to prevent a flash of authenticated content.
- The Supabase anon key grants read/write access — do not store sensitive logic purely in the frontend; rely on `created_by` checks in the Task Module as the authoritative gate.

## Testing Decisions

### What Makes a Good Test

Tests must verify **external behaviour** — what a module does from the perspective of its caller — not internal implementation details. A test must remain valid after internal refactoring. Tests must be fast, deterministic, and isolated: Supabase client calls are mocked at the module boundary; localStorage is mocked or reset between tests.

### Modules to Test

**Auth Module** (unit tests — highest priority)
- `signup`: hashes password before storing; rejects on duplicate email; rejects on duplicate username; writes correct user object (without password hash) to localStorage on success.
- `login`: accepts email as identifier; accepts username as identifier; rejects wrong password; does not write session on wrong password; writes session (without password hash) on success.
- `logout`: removes session from localStorage.
- `getSession`: returns null when localStorage is empty; returns the correct user object when a session exists.

**AuthContext** (component tests with React Testing Library)
- Provides `isManager = true` when role is `manager`; `isEmployee = true` when role is `employee`.
- Restores session from localStorage on mount.
- Redirects unauthenticated users to `/login` when accessing a protected route.

**Task Module** (unit tests with Supabase client mocked)
- `listTasks`: managers receive tasks from all departments; employees receive only tasks from their own department.
- `createTask`: inserts task with `created_by` and `department_id` taken from the current user's session.
- `updateTask` (employee path): updates `status` and `status_note` on own assigned task; does not update other fields; does not update tasks not assigned to them.
- `updateTask` (manager path): updates any field on a task they created.
- `deleteTask`: succeeds for manager on their own task; throws or returns error for employee caller.

**Department Module** (unit tests with Supabase client mocked)
- `listDepartments`: returns all departments.
- `createDepartment`: inserts new department; returns error for duplicate name.

**Dashboard Page** (component tests with React Testing Library)
- Renders five status cards with correct counts from mocked data.
- Clicking a status card navigates to `/tasks?status=<status>`.
- Overdue section renders only tasks with a past due date and non-completed status.
- Department breakdown table renders only for managers, not for employees.

**Task List Page** (component tests with React Testing Library)
- Renders one table row per task from mocked data.
- "Update Status" button renders only on rows where the task's `assignee_id` matches the logged-in employee.
- "Edit" and "Delete" buttons render only for managers on tasks they created.
- Filtering by status reduces the visible rows to only matching tasks.
- "New Task" button is visible for managers and absent for employees.

### Testing Tools

- **Vitest** — test runner (already configured in the project via `vite.config.ts`).
- **React Testing Library** — component and integration tests.
- **`vi.mock` / `vi.fn`** — mock Supabase client and localStorage.
- Test setup file already exists at `src/test/setup.ts`.
