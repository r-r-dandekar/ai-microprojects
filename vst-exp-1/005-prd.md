# PRD: RD-Processor-Mk-01

## Problem Statement

Guitarists who want a custom, flexible signal chain face a choice between rigid hardware pedal boards (fixed routing, limited to serial chains) and complex DAW session setups that are cumbersome to configure mid-performance. There is no lightweight, purpose-built VST that gives guitarists a visual, graph-based signal chain editor where they can freely combine serial and parallel routing, sidechain-linked dynamics, and cabinet simulation — all in a single plugin with a clean, minimal UI.

## Solution

RD-Processor-Mk-01 is a VST 3 guitar effects plugin (with standalone mode) built in C++ using JUCE. It presents a visual signal path canvas where guitarists construct a directed acyclic graph of effects blocks — distortion, EQ, compressor, decompressor, and impulse response convolution — connected in any serial or parallel combination. A left sidebar exposes the parameters of whatever block is selected. The plugin handles real-time audio processing with full stereo support, lock-free graph updates, and JSON-based preset management.

## User Stories

### Signal Chain Construction
1. As a guitarist, I want to add an effect block to my signal chain by clicking an "Add Block" button and selecting from a list, so that I can build up my processing chain incrementally.
2. As a guitarist, I want the signal path to be automatically laid out left-to-right, so that I can always read my chain from input to output without managing node positions.
3. As a user, I want to add a split node at any point in my signal chain, so that I can send the signal down two or more parallel effect paths simultaneously.
4. As a user, I want to add a merge node that combines multiple parallel paths back into one, so that I can blend the results of parallel effect chains.
5. As a user, I want to select the merge mode per merge node (sum, average, or weighted mix), so that I can control how parallel signals are combined without risking clipping.
6. As a user, I want to set a per-input gain on a weighted mix merge node, so that I can blend parallel paths at different levels.
7. As a user, I want to remove any effect block from the chain, so that I can restructure my signal path freely.
8. As a user, I want my signal chain to always have exactly one source block and one output block that cannot be deleted, so that I always have a valid routing.
9. As a user, I want the plugin to prevent feedback loops (cycles) in the graph, so that I never accidentally create an unstable routing.
10. As a user, I want to connect arbitrary numbers of parallel branches, so that I can build complex multi-path routings without being restricted to a fixed number of splits.

### Effects
11. As a guitarist, I want a distortion block with Drive, Tone, Output Level, and Curve parameters, so that I can dial in my overdrive character.
12. As a guitarist, I want to choose between soft clip (tanh), hard clip, and asymmetric clip distortion curves, so that I can select the harmonic character that suits my tone.
13. As a guitarist, I want a single-band EQ block with selectable filter type (Low Shelf, High Shelf, Band Shelf), Frequency, Gain, and Q parameters, so that I can shape the frequency response of my signal.
14. As a guitarist, I want to chain multiple EQ blocks in series, so that I can build a multi-band EQ from individual single-band blocks.
15. As a guitarist, I want a compressor block with Threshold, Ratio, Attack, Release, Makeup Gain, and Detection Mode (Peak or RMS) parameters, so that I can control the dynamics of my playing.
16. As a guitarist, I want a decompressor block that I can link to a specific upstream compressor's envelope, so that I can apply complementary expansion after earlier compression.
17. As a guitarist, I want to select which compressor a decompressor is linked to via a dropdown in the sidebar, so that the link is always explicit and unambiguous.
18. As a guitarist, I want an IR (impulse response) block that loads a cabinet simulation from a .wav file, so that I can apply realistic speaker cabinet coloration.
19. As a user, I want to browse my filesystem to select an IR .wav file for an IR block, so that I can use any cabinet IR I own.
20. As a user, I want mono and stereo IR files to be handled correctly, so that stereo IRs use both channels and mono IRs are broadcast to both channels.

### Real-Time Processing
21. As a guitarist, I want all processing to happen in real time with low latency, so that I can use the plugin live without noticeable delay.
22. As a guitarist, I want to modify my signal chain while audio is playing without any audio dropouts or glitches, so that I can make adjustments mid-performance.
23. As a DAW user, I want the plugin to report its processing latency to the host, so that my DAW can apply latency compensation and keep tracks in sync.
24. As a user, I want the left and right audio channels to be processed independently through all effect blocks, so that any stereo information already in my signal is preserved.

### Preset & State Management
25. As a DAW user, I want my signal chain and all parameter values to be saved and restored automatically with my DAW project, so that I never lose my settings.
26. As a user, I want to save my current signal chain as a named preset to disk, so that I can recall it in a future session.
27. As a user, I want to load a previously saved preset from disk, so that I can quickly recall a known tone.
28. As a user, I want presets stored as JSON files in a predictable folder (Documents/RD-Processor-Mk-01/Presets/), so that I can find, back up, and share them easily.
29. As a user, I want a preset to store the full graph topology, all effect parameter values, and IR file paths, so that loading a preset fully restores my setup.
30. As a user, I want a loaded preset to succeed even if an IR file is missing, with the IR block showing a warning instead, so that I don't lose my entire preset over one missing file.

### Undo / Redo
31. As a user, I want to undo adding, removing, or rewiring a node, so that I can recover from accidental structural changes.
32. As a user, I want to undo a parameter adjustment, so that I can revert a tweak that made things worse.
33. As a user, I want to redo any undone action, so that I can move forward again after exploring alternatives.

### UI — Sidebar
34. As a user, I want the sidebar to show the parameters of whichever effect block I have selected, so that I can focus on one block at a time.
35. As a user, I want the sidebar to be empty when no block is selected, so that the UI stays clean.
36. As a user, I want parameter controls to use appropriate input types (sliders for continuous values, dropdowns for enumerated choices), so that adjustment feels natural.
37. As a user, I want the decompressor's linked compressor to be shown as a dropdown of available upstream compressors in the sidebar, so that I can change the link at any time.

### UI — Warnings & Error States
38. As a user, I want a decompressor that has lost its linked compressor (because it was deleted) to show a visible warning on its node, so that I can quickly identify and fix the broken link.
39. As a user, I want an IR block whose file is missing to show a visible warning on its node, so that I know the block is inactive and why.

### UI — Metering
40. As a guitarist, I want to see a level meter on the source node, so that I can confirm my guitar signal is coming in and check for input clipping.
41. As a guitarist, I want to see a level meter on the output node, so that I can monitor my output level and check for output clipping.

### Standalone Mode
42. As a guitarist playing live (not in a DAW), I want to run the plugin as a standalone application, so that I can use it without a DAW.
43. As a standalone user, I want to select my audio input and output devices from the standalone app's settings, so that I can route my guitar in and my audio out to the right hardware.

## Implementation Decisions

### Technology
- Language: C++, Framework: JUCE, Build System: CMake with `juce_add_plugin`
- Target: Windows only for the initial version
- Plugin formats generated: VST3 + Standalone

### Audio Pipeline
- Channel configuration: stereo in, stereo out throughout the entire graph
- All effect blocks (distortion, EQ, compressor, decompressor, IR) process left and right channels independently with shared parameters
- Buffer size: host buffer size passed directly — no internal re-blocking
- Sample rate: accepted from host at `prepareToPlay`, used to parameterize all DSP

### Graph Model (AudioGraph Module)
- Nodes and directed edges forming a DAG; feedback loops rejected at the UI before they can be committed to the model
- Always contains exactly one Source node and one Output node
- Graph mutations (add node, remove node, rewire edge) are built on a copy on the UI thread, then atomically swapped via a lock-free pointer exchange for the audio thread — no mutexes on the audio thread
- Latency is recalculated and reported via `setLatencySamples` after each topology change
- Graph traversal during `processBlock` follows signal flow order (topologically sorted)

### Effect DSP Modules
- **DistortionProcessor:** Applies a transfer function per sample; curves (soft clip/tanh, hard clip, asymmetric) are registered via an enum + factory pattern so new curves are added in one place
- **EQProcessor:** JUCE `dsp::IIR` biquad filter; coefficients recalculated on parameter change
- **CompressorProcessor:** Envelope follower (peak or RMS selectable), gain computer, gain smoothing; envelope value shared via a thread-safe handle for decompressor access
- **DecompressorProcessor:** Reads envelope from a linked CompressorProcessor via the handle; behaves as pass-through (no-op) if the link is broken
- **IRProcessor:** JUCE `dsp::Convolution` (partitioned convolution / overlap-add); IR loaded asynchronously on a background thread; pointer to the loaded convolution engine swapped lock-free once ready; supports mono IR (broadcast to L+R) and stereo IR (independent channels)

### Graph Node Types
- **SplitNode:** Copies the input buffer identically to all output edges — no gain applied
- **MergeNode:** Combines input buffers using the configured mode: sum, average, or weighted mix (per-input gain stored as node parameters)

### Sidechain / Dependency Model
- Compressor → Decompressor link represented as an explicit Wire object in the data model
- Wire stores the source compressor's node ID; decompressor sidebar renders a dropdown of all upstream compressor nodes

### Preset Management (PresetManager Module)
- DAW state: full graph topology + all parameter values serialized to a binary blob via JUCE `getStateInformation` / `setStateInformation`
- User presets: JSON files written to `Documents/RD-Processor-Mk-01/Presets/`
- JSON schema includes: node list (type, ID, parameters), edge list (source node ID, target node ID, port indices), wire list (compressor node ID, decompressor node ID), IR file paths
- On load: missing IR file → IR node enters warning state (no-op), load continues for all other nodes

### Undo / Redo (UndoManager Module)
- Command pattern: every graph mutation and parameter change produces a reversible Command object
- Commands stored in a linear history stack; undo pops and reverses, redo re-applies
- Scope: graph topology changes and parameter adjustments; UI-only interactions (selection, scrolling) are not undoable

### Threading
- Audio thread: reads the current graph pointer, processes audio, reads `AudioProcessorParameter` values — never blocks
- UI thread: builds new graph copies, swaps pointer atomically, writes parameter values via JUCE `AudioProcessorParameter`
- Background thread: loads IR `.wav` files; swaps the convolution engine pointer once loaded

### Parameter Automation
- No DAW host automation — parameters are not exposed as automatable VST3 parameters
- JUCE `AudioProcessorParameter` used solely for thread-safe UI→audio value passing

## UI Aspects

### Layout Overview
- Three regions: Top Menu (narrow bar), Left Sidebar (fixed width), Signal Path Canvas (fills remaining space)
- No resizable panels for now — fixed proportions keep implementation simple

### Top Menu
- Global actions: open/save preset, settings
- No per-block controls live here

### Left Sidebar
- Rendered using JUCE built-in components (Slider, ComboBox, TextEditor, ToggleButton)
- Displays parameters of the currently selected node; completely empty when nothing is selected
- Parameter controls map to node type:
  - **Source/Output:** no editable parameters (meters shown on canvas, not sidebar)
  - **Distortion:** Drive (slider), Tone (slider), Output Level (slider), Curve (dropdown: Soft Clip / Hard Clip / Asymmetric)
  - **EQ:** Type (dropdown: Low Shelf / High Shelf / Band Shelf), Frequency (slider), Gain (slider), Q (slider)
  - **Compressor:** Threshold (slider), Ratio (slider), Attack (slider), Release (slider), Makeup Gain (slider), Detection Mode (dropdown: Peak / RMS)
  - **Decompressor:** Threshold (slider), Ratio (slider), Attack (slider), Release (slider), Makeup Gain (slider), Linked Compressor (dropdown — lists all upstream compressor node names; shows "None / Unlinked" if no compressors exist upstream)
  - **IR:** File path display (read-only text), Browse button (opens file chooser for .wav), status indicator (active / loading / file missing)
  - **Merge:** Per-input gain sliders (one per input path, visible only when mode is Weighted Mix), Mode dropdown (Sum / Average / Weighted Mix)
  - **Split:** No parameters
- Sidebar updates immediately on node selection change

### Signal Path Canvas (Custom Drawn)
- Custom JUCE Component using the Graphics API (not standard JUCE components)
- Nodes rendered as labeled rectangles; edges rendered as horizontal lines with arrows indicating signal direction
- Auto-layout: nodes are arranged left-to-right in topological order; vertical spacing distributes parallel branches evenly
- Source node always at the leftmost position; Output node always at the rightmost position
- Clicking a node selects it (highlights it, populates the sidebar)
- Clicking empty canvas deselects
- "Add Block" button on the canvas opens a popup/overlay listing all addable block types (Distortion, EQ, Compressor, Decompressor, IR, Split, Merge)
- Controls for adding/removing splits and merges are accessible via right-click context menu on nodes or edges
- Warning state nodes (unlinked decompressor, missing IR) rendered with a red border or red indicator — distinct from normal and selected states
- Level meters on Source and Output nodes rendered as vertical bar indicators within those nodes on the canvas

### Visual Constraints
- No free-form drag of nodes — positions are always determined by auto-layout
- Graph always reads left-to-right; no vertical-primary layouts
- No overlapping nodes — auto-layout must guarantee clean spacing
- Parallel branches are stacked vertically between their split and merge nodes
- Edges are straight horizontal lines within a branch; vertical connectors between branches at split/merge points
- Selected node has a distinct highlight (e.g. accent-colored border) — never ambiguous
- Warning state takes visual precedence over selected state if both apply simultaneously

### MVC Responsibilities
- **Model:** Owns the graph topology, all node parameter values, wire links, and preset state. The audio thread reads from the model's atomic graph pointer.
- **View:** All JUCE components (canvas, sidebar controls). Reads from the model; never writes directly. Fires events/callbacks on user interaction.
- **Controller:** Receives UI events (add block, delete block, parameter change, link compressor, browse IR, save/load preset). Validates actions (e.g. DAG check before adding an edge), applies them to the model, pushes Commands to the UndoManager, triggers graph rebuild and atomic swap.

## Testing Decisions

### What Makes a Good Test
Tests should verify observable external behavior through a module's public interface — not internal implementation details. A test that breaks when the internal algorithm is refactored but the output behavior is unchanged is a bad test. Tests should be deterministic and not depend on timing.

### Modules to Test

**AudioGraph**
- Adding and removing nodes produces correct topology
- DAG validation rejects edges that would create a cycle
- Topological sort returns nodes in valid processing order for various graph shapes (linear, parallel branches, nested splits)
- Lock-free swap: new graph is observed by the audio thread after the swap; old graph is not mutated

**DistortionProcessor**
- Each curve (soft clip, hard clip, asymmetric) maps known input values to expected output values
- Drive, Tone, and Output Level parameters affect output as expected
- Adding a new curve via the factory produces correct output

**EQProcessor**
- Each filter type (Low Shelf, High Shelf, Band Shelf) passes/attenuates frequencies as expected at known parameter settings (verified by measuring output spectrum or specific frequency magnitudes)
- Coefficient update on parameter change takes effect on the next processed block

**CompressorProcessor**
- Gain reduction is applied above threshold at the configured ratio
- Peak and RMS detection modes produce different responses to the same transient signal
- Attack and release times govern the speed of gain change within expected tolerances
- Envelope value is readable from the shared handle immediately after processing a block

**DecompressorProcessor**
- Passes signal through unchanged when unlinked (no-op)
- Applies complementary expansion when linked to a compressor and envelope is available

**IRProcessor**
- After loading a valid mono IR, output is the convolution of the input with that IR
- After loading a valid stereo IR, L and R channels use the respective IR channels
- While loading (async), processor operates as pass-through
- When given an invalid path, processor remains in no-op / warning state

**SplitNode / MergeNode**
- Split output buffers are identical copies of the input buffer
- Merge sum mode: output equals sum of inputs
- Merge average mode: output equals sum divided by number of inputs
- Merge weighted mix: output reflects per-input gain settings

**PresetManager**
- Serializing a graph and deserializing it produces an identical graph structure and parameter values
- A preset with a missing IR file path deserializes successfully; the IR node is in warning/no-op state
- JSON output is valid JSON and contains all required fields

**UndoManager**
- Undo after adding a node removes it
- Undo after a parameter change restores the previous value
- Redo re-applies the undone action
- Undo at the beginning of history is a no-op
- Redo at the end of history is a no-op
